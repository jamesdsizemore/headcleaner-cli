# Checking converted output

This page teaches you how to read the output folder headcleaner produces. It is written for someone who has just run their first conversion and is looking at a directory of unfamiliar files. By the end of the page you will know what every artifact is, why it exists, and when to use it.

## What is in the output folder

After a successful run, the output folder you specified (in the examples we have been using, `./my-folder.clean`) contains four kinds of artifact at the top level: a manifest, a report, and two derivative folders. The exact layout is:

```text
./my-folder.clean/
├── manifest.json          # one entry per source file, structured
├── REPORT.md              # human-readable summary of the run
├── _md/                   # plain Markdown, one file per source
│   ├── notes.docx.md
│   ├── report.pdf.md
│   └── page.html.md
└── okf/                   # OKF v0.2 bundle, one concept per source
    ├── index.md           # auto-generated directory index
    ├── notes.docx.md
    ├── report.pdf.md
    └── page.html.md
```

The top-level layout is identical regardless of which input formats you used, because every format lands in the same two derivative trees after the canonical conversion step.

## The plain Markdown tree: `_md/`

The `_md/` folder is one Markdown file per source. Each file is the source document rendered as Markdown with a YAML frontmatter block at the top. If you want clean Markdown you can read in any editor, paste into a wiki, or commit to a documentation repository, this is where you look.

Inside each `_md/<source>.<ext>.md` file, the structure is always the same:

```text
---
[YAML frontmatter — source URI, source hash, trust state, generation date, etc.]
---

# Headings from the source

Markdown-rendered body content.
```

The frontmatter is the part headcleaner controls. The body is the readable projection of your document. You can edit the body freely and headcleaner will not overwrite your edits as long as the source hash recorded in the frontmatter still matches the source file; if the source changes, the frontmatter records the new hash and the body is regenerated.

## The OKF bundle: `okf/`

The `okf/` folder is the same content as an OKF v0.2 knowledge bundle. OKF bundles are designed to be portable between knowledge-management tools, so if you intend to feed your headcleaner output into a downstream system that understands OKF, this is what you want. The format is described in the OKF v0.2 specification; headcleaner emits the full trust family on every concept.

The bundle contains two kinds of files:

- `index.md` is auto-generated by headcleaner when the run finishes. It lists every concept in the bundle with its title, type, and status, and links to the per-concept files. If you want to know "what is in this bundle?" without opening every file, `index.md` is the answer.
- One `<source>.<ext>.md` file per source, named without the source extension. The `.docx.md` filename in `_md/` becomes `notes.docx.md` in `okf/`; in `okf/`, the trailing `.docx` is preserved as part of the conceptual identity. OKF readers rely on the extension-suffixed name to disambiguate concepts.

The body of each `okf/` file is identical to the body of the corresponding `_md/` file. The difference is in the frontmatter, which uses the full OKF v0.2 trust family. You can switch between the two trees depending on whether your downstream consumer speaks plain Markdown or OKF.

## The run manifest: `manifest.json`

`manifest.json` is the authoritative record of the run. It is structured, machine-readable, and designed to be consumed by other tools. The two main sections are:

```json
{
  "schema_version": "1",
  "started_at": "2026-08-20T14:32:01Z",
  "finished_at": "2026-08-20T14:32:04Z",
  "tool_version": "0.x.y",
  "results": [
    {
      "relpath": "notes.docx",
      "engine": "officecli",
      "status": "ok",
      "sha256": "aaa...",
      "md_path": "_md/notes.docx.md",
      "okf_path": "okf/notes.docx.md",
      "duration_seconds": 0.4
    },
    {
      "relpath": "scan.pdf",
      "engine": "pdfplumber",
      "status": "skipped",
      "sha256": "bbb...",
      "error": "no OCR engine installed; install Tesseract"
    }
  ],
  "options": {
    "format": "both",
    "ocr": false,
    "dedupe_threshold": 0.8
  }
}
```

The `results` array has one entry per source file. Each entry records what headcleaner did with that file: the relative path, which engine handled it, the resulting status, the source file's SHA-256 hash, the path to the Markdown output (if any), the path to the OKF output (if any), the elapsed time, and the error message (if any). The `options` object records the run settings for reproducibility.

If you are writing a tool that consumes headcleaner output, the manifest is the source of truth. The complete field reference is in the [result reference](../reference/result-reference.md).

## The run report: `REPORT.md`

`REPORT.md` is the same information as the manifest, but in a human-readable Markdown form. It opens with run metadata (bundle, start, finish, wall-clock), then summarizes the conversion with a status table, then breaks down results by engine, and finally lists the top errors if any.

You should read `REPORT.md` first when you want to know whether a run was healthy. The summary table at the top tells you the answer in three numbers: files processed, files skipped, files failed. The [Understanding results](understanding-results.md) page explains what those numbers mean.

## The hidden state directory: `.headcleaner/`

Inside the OKF bundle, headcleaner also creates a hidden directory called `.headcleaner/` for derivative state. By default you should not need to look inside it, but knowing it exists is useful because it is the canonical home for the search index, the sync state, and any per-bundle policy overrides you create.

The contents depend on what commands you have run:

- `.headcleaner/index.sqlite3` appears after you run `headcleaner index rebuild`.
- `.headcleaner/sync.json` appears after every successful conversion run.
- `.headcleaner/policies/` is the directory headcleaner looks in for project-specific policy overrides.

These files are all rebuildable. Deleting them is safe; rerunning the appropriate command regenerates them.

## Putting it together

When you come back to an output folder a week after running headcleaner, the workflow that gets you back up to speed is:

1. Open `REPORT.md` first. Confirm the run summary looks the way you expect.
2. Open `okf/index.md` if you want a navigable overview of every concept in the bundle.
3. Open a specific `_md/<file>.md` if you want to read one document.
4. Open `manifest.json` if you need structured data for a downstream tool.

The `_md/` and `okf/` folders contain your documents. The manifest and report describe the conversion that produced them. The hidden `.headcleaner/` directory is the durable state that lets headcleaner do smart things on subsequent runs.

## Phase 3 signals

Phase 3 adds three read-only signals you can run after `convert` to get a richer picture of what to do next. None of them change `verified:` or the canonical output.

- `headcleaner readiness BUNDLE [--profile NAME]` produces a per-concept grade (`blocked | needs_review | conditional | ready`) with every deduction cited. Use it before `headcleaner review` to filter out concepts that already satisfy the profile you care about.
- `headcleaner review-queue BUNDLE [--json]` produces a deterministic, evidence-based queue. Use it to triage a large bundle before sending individual items to a human reviewer.
- `headcleaner attest BUNDLE --in-toto PATH` writes a deterministic in-toto Statement alongside the attestation. Use it when you need to hand the bundle to a downstream system that expects an in-toto-compatible integrity statement.
